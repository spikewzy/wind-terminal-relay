# Gitee 检查更新，自己决定何时安装

## 先安装一次带更新入口的管理台

已有旧部署：把 `wind-relay-gateway-upgrade-0.1.4.zip` 传到云电脑，解压到新文件夹，双击 **Upgrade-Gateway.cmd**。先让同事暂停新任务；Wind、信创服务、Tailscale 保持运行。网关与管理台会短暂重启，原 JSON 接入文件继续有效。

如果这次只想安装管理台，也可解压 `wind-relay-console-0.3.2.zip`，双击 **Update.cmd**；此操作不升级网关。之后可以在页面中选择网关升级。

云电脑访问不了 GitHub，可以从别的电脑下载后传过去。只有这次需要手动放入安装包；旧管理台没有在线更新入口，无法靠检查按钮安装自己尚不具备的功能。

## 以后在管理台点几下

1. 打开云电脑桌面的 **WindRelay-Console**，进入 **软件更新**。
2. 自动检查在管理台启动时、以及之后每 6 小时进行；也可以点 **检查更新**。检查只读取版本目录，不下载 ZIP，不安装，不调用 Wind。
3. 看更新说明、选版本。已安装的版本和会导致降级的版本不能安装。
4. 让同事暂停新任务，再点 **下载并更新所选版本 → 确认下载并更新**。
5. 保持云电脑开机。页面会显示下载、校验、安装、完成等状态。安装时页面短暂断开是正常的；它会自动尝试重新连接，最后核对正在运行的版本。

检查或下载失败时，原服务继续运行。还有排队、执行或不确定任务时会停止升级；不取消或重做任务。设备名单有待重载变更时，先完成原来的“重载网关 → 核对生效”，再升级。

只自动检查，不自动安装。更新失败、关机中断或运行版本未完整核对时也不自动重试。保留现场，查看“实际部署信息”，导出诊断包。网关可能已完成、管理台却未完成；不能一看到失败就反复点击更新。

## 更新文件从哪来

固定 Gitee 仓库的 `main` 分支：

- 版本目录：`updates/stable.json`
- 升级包：`updates/packages/wind-relay-gateway-upgrade-版本.zip`

Gitee 原始文件会跳转到它自己的 `raw.giteeusercontent.com` 内容域名，程序只允许同一仓库路径的这个官方内容入口。下载时不发送任何中继 token 或管理台密钥，不回退到 GitHub。下载字节数、SHA256 和包内清单均会核对；不接受页面输入任意安装地址。

HTTPS 与哈希用于确认下载来源和内容一致性；信任边界是仓库维护权限，不是独立的发行签名。请维护好 GitHub 和 Gitee 仓库权限。

Gitee 不通或尚未同步：页面提示失败，原服务继续运行。不同步不会自动改用别的下载来源。同步完成后点“检查更新”即可。

### Windows 证书校验失败

管理台 0.3.2 在保留系统证书库的同时，加载随软件发布的 Mozilla/certifi 公共 CA 证书包，以改善云电脑后台 Python 信任库不完整的问题。证书包来源、版本和 SHA256 记录在 `monitor/ca-provenance.json`，许可在 `monitor/CA-LICENSE.txt`。不会向 Windows 根证书库写入证书；HTTPS 仍校验证书链、域名、有效期，并保留 Python 默认的严格校验。

已确认的 `SSLCertVerificationError` 只能证明校验失败，旧诊断没有保留具体校验码，不能仅据此断定缺哪个根证书。若补充标准证书后仍失败，新版会显示证书、时钟、域名、DNS、超时或 HTTP 的对应错误，并在诊断包保留校验码，方便继续排查企业代理、时间或证书链。

当前更新器如果已经因证书失败而不能下载新版，需先从另一台电脑传入修复版管理台 ZIP 并运行 `Update.cmd`；或用完整网关升级包的 `Upgrade-Gateway.cmd` 一次升级两个组件。完成后按 **F5 刷新浏览器页面**，再检查更新。

Python 依赖已匹配时复用；不匹配时会在停旧网关前准备独立环境，可能需要连接 Python 软件包下载源。**从 Gitee 下载更新不等于完全离线安装**。依赖准备失败时旧网关不停止。

## 更新任务与维护记录

安装通过独立 Windows 任务 **WindRelayUpgrade** 执行，不依赖管理台窗口或旧管理台服务继续存活。它没有定时触发、没有自动失败重试；只有本机已解锁页面确认后才启动。管理台沿用 SYSTEM 后台任务，浏览器无需弹出 PowerShell。

只允许同时执行一次更新；期间不能修改设备名单。下载、所选版本和安装结果保存在 `.relay/online-updates`，安装日志在相应任务目录的 `installer.log`。这里属于本地维护资料，不要整目录发群或上传仓库。对外发管理台导出的诊断 ZIP 或部署报告，它们只保留经过筛选的版本、状态与错误类别。

程序继续复用网关升级机制：空闲核查、独立版本目录、数据库备份、维护期验证、恢复接单前失败回退，以及恢复接单后不回退数据库。不会停止信创执行端、Wind 或 Tailscale，不重置接入凭据。

## 发布者：只更新 GitHub，再同步 Gitee

每次发布先更新网关/管理台相应版本，完成测试，然后运行：

```text
python gateway_update/publish_feed.py --published-on 2026-10-16 --notes "本次变化的简短说明"
python gateway_update/publish_feed.py --check
```

日期应填本次发布的日期。脚本生成确定性的 ZIP，并把该版本的字节数、哈希、构建号写进 `updates/stable.json`。同一版本 ZIP 不可覆盖，内容改变要提升网关包版本；保留最多五条版本目录记录。

把 `updates/stable.json`、`updates/packages/` 对应 ZIP 和本次代码一起提交 GitHub 的 `main` 分支，等检查通过，再将 GitHub 同步到 Gitee。**只同步 Git 代码就能带上版本目录和 ZIP**，无需额外复制 GitHub Release 的附件。CI 会检查提交的 ZIP 与源码是否一致。

不要在 Gitee 另改更新文件，也不要只同步 JSON 而漏掉 ZIP。更新目录同步一半时客户端会拒绝不一致的内容，稍后完整同步再检查即可。首次 Gitee 同步与云电脑实机升级仍需操作完成后确认，源码发布和离线验证不代表现有部署已经升级。
