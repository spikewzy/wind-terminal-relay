# 额度未知时如何观察

目前已知的是一般计算窗口：从当前时刻向前滚动 7×24 小时，即 168 小时。依据为用户在 2026-10-14 提供的“API数据流量的计算方法”截图，与已安装 core 的一般规则说明一致。截图不提供本账户各函数的具体上限、官方计费单元或不同函数之间的额度分组。

## 已知与未知

| 项目 | 本项目如何处理 |
|---|---|
| 一般观察窗口 | 默认滚动 168 小时，可另外查看较短时间窗 |
| 午夜、周一或某固定日期清零 | 没有这项证据，不按自然日刷新 |
| 本账户具体可用额度与剩余额度 | 未知，保持 null |
| Wind 实际计费单元及额度组 | 未知，不把请求数、预留次数或估算 cells 等同于官方扣量 |
| 超限后的确切恢复时间 | 未知，不承诺失败后恰好 168 小时恢复 |
| 人工终端、本地直连及其他程序用量 | 不在 relay 的完整观测范围内 |

滚动窗口意味着较早使用量会逐渐移出窗口；何时降到实际阈值以下，取决于账户历史使用量和未知的官方阈值。最后一次超限时间本身不足以计算恢复时刻。

## 记录方式

客户端任务同时入队，执行端顺序执行。任务统计按入队时间整理；调用预留观测按每次进入 core 预算预留阶段的执行端时间整理。每次预留携带独立事件编号，结果重发不会重复累计。同一任务可能有多次预留，也可能因缓存或本地元数据读取没有预留。

预留不是精确 SDK 调用：失败、超时、登录检查或未取得锁的尝试也可能包含其中。估算 cells 是请求网格，不是 Wind 官方流量。mock 和 native 分开统计，历史回执复读不新增历史调用量。

云端只在任务结果回传后收到事件；正在执行、断网或遗留不确定任务可能已有使用量但云端尚不知道，报告明确标记延迟和未知。两台机器的时间需正常同步；这里的观测时间不替代 Wind 服务端账单时间。

额度超限观察仅记本次失败执行中的 quota 错误。成功的能力/状态/回执读取可能包含历史 quota 错误，不能据此计新失败或再次停机。观测报告不推断当前账户余额、恢复状态或恢复时刻。

## 超限后的操作

保留当前失败回执和 halt 标记，暂停继续发起大批量任务。可以直接读取已经回传的云端结果或客户端已保存的副本；执行端停机后不会领取任务，经中继读取执行端磁盘缓存或回执也需等待恢复，不能承诺这些读取仍可用。不自动更换数据源、不重复失败任务、不按 168 小时定时清除标记。恢复执行须在核查原任务和 Wind 当前可用情况后明确操作；一次请求恢复不能证明所有函数或额度组都恢复。

需要人为设置服务软限制时，可使用原 core 的共享 `query-budget.json`；这些是用户自定的保护上限，不能称为 Wind 官方额度。本版本保持官方具体上限未知，不根据截图编造默认数值。
